# HTML5 семантика та структура для Mobile First Single Page розробки

Mobile First HTML5 семантика стала фундаментальною основою сучасної веб-розробки. Дослідження показує, що правильна семантична структура забезпечує **60-80% швидший initial render** порівняно з div-based layouts, а Schema markup підвищує CTR на **25-82%** залежно від галузі. 59.45% веб-трафіку походить з мобільних пристроїв, що робить Mobile First підхід критичним для комерційного успіху.

Дослідження охоплює п'ять ключових напрямків: семантичні теги для mobile-first архітектури, WCAG 2.1 accessibility вимоги, мета-теги та SEO оптимізацію, Schema.org мікродані для підвищення конверсій, та Open Graph оптимізацію для соціальних мереж. Кожен напрямок підкріплений реальними кейсами (Rotten Tomatoes досягли **25% збільшення CTR**, Food Network — **35% зростання візитів**) та готовими до використання code templates.

## Семантичні теги для Mobile First single page архітектури

Сучасна HTML5 семантика базується на принципі progressive enhancement та semantic-first frameworks. У 2024-2025 роках спостерігається тренд на zero-runtime overhead з акцентом на server-side rendering та мінімізацію client-side JavaScript. Web Components використовують семантичні елементи як foundation, забезпечуючи accessibility by default.

### Оптимальні семантичні теги для mobile-first структури

**Header елемент** визначає вступний контент або навігаційну секцію. На мобільних пристроях header має бути компактним і часто collapsible. Він надає implicit `banner` role коли розміщений на top level. Критично важливо тримати header мінімальним — в ідеалі тільки логотип та hamburger menu.

**Nav елемент** призначений для головних навігаційних посилань з implicit `navigation` landmark role. Для Mobile First дизайну рекомендується використовувати hamburger menus або bottom navigation. Завжди додавайте `aria-label` для множинних nav елементів на сторінці, наприклад `aria-label="Primary"` та `aria-label="Footer"`.

**Main елемент** представляє домінантний контент документа і повинен використовуватися лише один раз на сторінці. Він надає implicit `main` landmark role і ніколи не повинен бути nested в інші семантичні елементи. Для SPA критично важливо програмно керувати фокусом на main при зміні маршруту.

**Article елемент** призначений для самодостатнього, незалежно розповсюджуваного контенту. Ідеально підходить для card-based mobile layouts — blog posts, product cards, user comments. Може містити власні header/footer та множинні sections. На мобільних пристроях articles природно стекуються вертикально для кращої читабельності.

**Section елемент** групує тематичний контент і завжди повинен включати heading (h2-h6). Використовується для chapters, tabs, numbered sections. На mobile краще стекувати sections вертикально замість складних grid layouts для оптимальної readability.

**Aside елемент** для tangentially related контенту — sidebars, callouts, related links, advertisements. На мобільних пристроях aside часто репозиціонується нижче основного контенту через обмеження ширини екрану.

**Footer елемент** надає implicit `contentinfo` role на document level. На mobile footer має бути мінімальним — уникайте heavy content, який сповільнює scroll та збільшує loading time.

### Критичні помилки що слід уникати

**Div-itis та span-itis** залишаються найпоширенішою помилкою. Замість `<div class="header">` завжди використовуйте `<header>`. Замість `<div class="nav">` — `<nav>`. Семантичні теги не тільки покращують accessibility, але й забезпечують кращу browser optimization та rendering performance.

**Використання семантичних тегів лише для стилізації** підриває їх призначення. Ніколи не використовуйте `<h1>` просто для великого шрифту — використовуйте CSS. Не використовуйте `<strong>` замість CSS для bold. Не використовуйте `<blockquote>` для indentation.

**Некоректний nesting** порушує HTML5 специфікацію. Main ніколи не повинен бути всередині header. Footer не повинен містити main. Завжди дотримуйтесь правильної ієрархії: header, main (з вкладеними sections/articles), footer.

**Multiple main елементи** — грубе порушення. Дозволений лише ОДИН main на сторінку. Для SPA рішення: динамічно оновлювати content всередині єдиного main елемента при зміні маршруту.

**Пропущені рівні headings** порушують accessibility. Ніколи не пропускайте рівні: після h1 йде h2, після h2 — h3. Не стрибайте з h1 на h3. Screen readers використовують heading hierarchy для навігації — 85.7% користувачів screen readers вважають heading levels дуже/досить корисними.

**Неправильні інтерактивні елементи** знищують accessibility. Ніколи не використовуйте `<div onclick="submit()">` замість `<button>`. Button елементи надають native keyboard support, touch support, та screen reader compatibility автоматично.

**Performance implications** семантичних тегів значні: 60-80% швидший initial render, краща browser caching, зменшена DOM complexity, покращена battery life на мобільних пристроях через менше JavaScript processing.

## WCAG 2.1 accessibility для Single Page Applications

WCAG 2.1 Level AA compliance критично важлива для mobile-first SPAs. Нові критерії в WCAG 2.1 безпосередньо орієнтовані на мобільні пристрої, включаючи orientation flexibility, reflow, pointer gestures, та motion actuation.

### Ключові WCAG 2.1 вимоги для SPAs

**SC 2.4.2 Page Titled (Level A)** вимагає динамічного оновлення `document.title` при кожній зміні маршруту в SPA. Це критично важливо для screen reader користувачів, які отримують announcement нової сторінки через title change.

```javascript
// Оновлення title при зміні маршруту
function handleRouteChange() {
  document.title = "Деталі Продукту - MyApp";
  
  // Фокус на main heading
  const mainHeading = document.querySelector('h1');
  mainHeading.setAttribute('tabindex', '-1');
  mainHeading.focus();
  
  // Announce для screen readers
  announcePageChange("Деталі Продукту");
}

function announcePageChange(title) {
  const announcement = document.createElement('div');
  announcement.setAttribute('role', 'status');
  announcement.setAttribute('aria-live', 'polite');
  announcement.textContent = `Перехід до ${title}`;
  document.body.appendChild(announcement);
  
  setTimeout(() => announcement.remove(), 1000);
}
```

**SC 1.4.10 Reflow (Level AA)** вимагає, щоб контент був читабельним на ширині 320px без горизонтального скролінгу. Це критично важливо для mobile-first підходу.

**SC 2.5.1 Pointer Gestures (Level A)** вимагає single-pointer альтернатив до multi-touch жестів. Якщо ви використовуєте pinch-to-zoom, надайте кнопки + та - як альтернативу.

**SC 2.5.3 Label in Name (Level A)** вимагає, щоб видимий label відповідав accessible name. Якщо кнопка показує "Купити Зараз", aria-label не повинен бути "Submit Purchase".

**SC 2.5.4 Motion Actuation (Level A)** вимагає альтернатив до motion-triggered actions. Якщо shake-to-undo доступний, надайте також кнопку undo.

### ARIA атрибути для Mobile First інтерфейсів

**Перше правило ARIA**: "Якщо ви можете використовувати native HTML елемент з потрібною семантикою та поведінкою, ВИКОРИСТОВУЙТЕ його замість репурпозування елемента та додавання ARIA." Дослідження WebAIM показує, що сторінки з ARIA в середньому мають **41% більше виявлених помилок** ніж сторінки без ARIA. "No ARIA is better than bad ARIA."

**Landmark roles** для навігації screen reader:

```html
<header role="banner">
<nav role="navigation" aria-label="Головна навігація">
<main role="main">
<aside role="complementary" aria-label="Схожі статті">
<footer role="contentinfo">
```

**ARIA states та properties** для інтерактивних компонентів:

```html
<!-- Expandable mobile menu -->
<button 
  aria-expanded="false" 
  aria-controls="mobile-nav"
  aria-label="Відкрити меню навігації">
  ☰
</button>
<nav id="mobile-nav" hidden>
  <a href="/" aria-current="page">Головна</a>
  <a href="/about">Про нас</a>
</nav>
```

**aria-live regions** для динамічного контенту:

```html
<!-- Polite: оголошує коли користувач idle -->
<div aria-live="polite" aria-atomic="true">
  5 нових повідомлень
</div>

<!-- Assertive: оголошує негайно -->
<div aria-live="assertive" role="alert">
  Помилка відправки форми
</div>
```

### Touch targets для mobile accessibility

WCAG 2.1 Success Criterion 2.5.5 Target Size (Level AAA) рекомендує мінімум **44 × 44 CSS pixels**. Хоча це AAA level (не обов'язково для AA), це критично важливо для mobile usability. Платформні guidelines: Apple iOS — 44×44 points, Google Material Design — 48×48 dp, Microsoft — 44×44 effective pixels.

```html
<!-- Візуальна іконка може бути меншою, але touch target 44x44 -->
<button style="min-width: 44px; min-height: 44px; padding: 12px;">
  <svg width="20" height="20"><!-- icon --></svg>
</button>

<!-- Icon buttons з proper spacing -->
<style>
.icon-btn {
  width: 48px;
  height: 48px;
  padding: 12px;
  margin: 4px; /* створює 8px gap між кнопками */
}

/* Full-width buttons на mobile */
@media (max-width: 768px) {
  .mobile-action {
    display: block;
    width: 100%;
    min-height: 44px;
    margin-bottom: 8px;
  }
}
</style>
```

**Мінімальний spacing між targets** — 8px для запобігання accidental taps.

### Focus management в Single Page Applications

Для SPAs існують два primary patterns focus management:

**Pattern 1: Emulate Native Page Load** — скинути фокус до top після route change. Простіший підхід, але менш оптимальний для screen reader користувачів.

**Pattern 2: Move Focus to New Content (Recommended)** — перемістити фокус на main heading нового view:

```javascript
// Router hook - фокус на main heading при зміні маршруту
router.afterEach(() => {
  // Оновити title
  document.title = newPageTitle;
  
  // Фокус на main heading
  const mainHeading = document.querySelector('h1');
  if (mainHeading) {
    mainHeading.setAttribute('tabindex', '-1');
    mainHeading.focus();
  }
  
  // Оголосити для screen readers
  announcePageChange(newPageTitle);
});
```

**Modal focus management** — trap focus всередині modal:

```javascript
let lastFocusedElement;

function openModal(modalId) {
  const modal = document.getElementById(modalId);
  const focusableElements = modal.querySelectorAll(
    'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])'
  );
  const firstElement = focusableElements[0];
  const lastElement = focusableElements[focusableElements.length - 1];
  
  lastFocusedElement = document.activeElement;
  modal.removeAttribute('hidden');
  modal.setAttribute('aria-modal', 'true');
  
  firstElement.focus();
  
  // Trap focus within modal
  modal.addEventListener('keydown', (e) => {
    if (e.key === 'Tab') {
      if (e.shiftKey && document.activeElement === firstElement) {
        e.preventDefault();
        lastElement.focus();
      } else if (!e.shiftKey && document.activeElement === lastElement) {
        e.preventDefault();
        firstElement.focus();
      }
    }
    if (e.key === 'Escape') {
      closeModal(modalId);
    }
  });
}

function closeModal(modalId) {
  const modal = document.getElementById(modalId);
  modal.setAttribute('hidden', '');
  lastFocusedElement.focus(); // Повернути фокус до trigger element
}
```

## Meta-теги та Mobile First SEO оптимізація

Mobile-first indexing від Google означає, що mobile версія сайту використовується для indexing та ranking. 59.45% веб-трафіку походить з мобільних пристроїв у 2024-2025. Правильні meta tags критично важливі для mobile SEO.

### Критичні meta tags для Mobile First

**Viewport meta tag** — найважливіший для mobile. Має бути розміщений на top of head, одразу після charset, ПЕРЕД stylesheets для запобігання layout reflow:

```html
<meta name="viewport" content="width=device-width, initial-scale=1.0">
```

**Mobile-Web-App-Capable tags** для PWA experience:

```html
<!-- iOS -->
<meta name="apple-mobile-web-app-capable" content="yes">
<meta name="apple-mobile-web-app-status-bar-style" content="black-translucent">

<!-- Android/Chrome -->
<meta name="mobile-web-app-capable" content="yes">
<meta name="theme-color" content="#000000">
```

**Character Encoding** має бути першим елементом у head (within перших 1024 bytes):

```html
<meta charset="UTF-8">
```

**Robots Meta Tags** — використовуйте ОДНАКОВІ robots meta tags на mobile та desktop для mobile-first indexing:

```html
<meta name="robots" content="index, follow, max-image-preview:large">
```

### Title та description оптимізація для mobile

**Title tag best practices**: mobile displays ~50-55 символів (vs 60-65 desktop). Оптимальна довжина 15-40 символів забезпечує **8.6% вищий CTR**. Question formats дають **+14.1% вищий CTR**. Позиція #1 в результатах пошуку має average CTR **31.7%**.

```html
<title>Primary Keyword: Clear Benefit | Brand</title>
```

**Meta description оптимізація**: desktop показує 155-160 символів, mobile ~130 символів. Google переписує 62.78% descriptions, тому робіть їх compelling та action-oriented:

```html
<meta name="description" content="Відкрийте 2024 essential mobile meta tags. Навчіться viewport, canonical, та structured data імплементації з готовими code examples.">
```

### Canonical tags для Single Page Applications

SPAs мають специфічні challenges: множинні URLs для того ж контенту (query params, fragments, tracking), динамічні route changes, потреба в real-time canonical updates.

**React implementation з React Helmet**:

```javascript
import { Helmet } from 'react-helmet-async';

function ProductPage({ product }) {
  const canonicalUrl = `https://example.com/products/${product.slug}`;
  
  return (
    <>
      <Helmet>
        <title>{product.name} | Store</title>
        <link rel="canonical" href={canonicalUrl} />
        <meta name="description" content={product.description} />
      </Helmet>
      <h1>{product.name}</h1>
    </>
  );
}
```

**Best practices для SPA canonicalization**: set canonical для кожного route, update динамічно при route change, використовуйте absolute URLs (не relative), keep consistent з sitemap, один canonical per page.

### Mobile-first indexing considerations

**Content Parity** — mobile ПОВИНЕН містити той же контент що й desktop: same text, images, videos, links, same headings (H1-H6), equivalent alt text, no missing content.

**Meta Data Equivalence** — title, description, robots tags МАЮТЬ співпадати на mobile та desktop.

**Critical Mobile-First Indexing Checklist**:
- Identical title tags mobile/desktop
- Identical meta descriptions
- Same robots meta tags
- Proper viewport tag
- Correct canonical tags
- Images accessible (not blocked)
- High-quality images (not low-res mobile versions)
- Same structured data on both versions

### Common mistakes в schema markup

**Hidden content** — ніколи не додавайте schema для invisible content. **Self-serving reviews** — власник не може залишати reviews своєму бізнесу. **Missing required properties** — включайте всі обов'язкові поля. **Mismatched content** — schema має точно відповідати page content. **Wrong item types** — використовуйте найспецифічніший type available. **Duplicate schemas** — один schema per entity. **Invalid dates** — використовуйте ISO 8601 format з timezone. **Relative URLs** — завжди absolute URLs.

### Dynamic OG tags для Single Page Applications

**Підхід 1: Server-Side Meta Tag Injection**:

```javascript
// server.js з Node.js/Express
const express = require('express');
const fs = require('fs');
const path = require('path');
const app = express();

// Route data configuration
const routes = {
  '/': {
    title: 'Головна Сторінка',
    description: 'Ласкаво просимо на наш вебсайт',
    image: 'https://yoursite.com/images/home.jpg'
  },
  '/about': {
    title: 'Про Нас',
    description: 'Дізнайтеся більше про нашу компанію',
    image: 'https://yoursite.com/images/about.jpg'
  }
};

// Middleware для injection meta tags
app.get('*', async (req, res) => {
  const filePath = path.join(__dirname, 'dist', 'index.html');
  
  try {
    let html = fs.readFileSync(filePath, 'utf8');
    const route = routes[req.path];
    
    if (route) {
      html = html.replace(
        '<meta property="og:title" content="">',
        `<meta property="og:title" content="${route.title}">`
      );
      html = html.replace(
        '<meta property="og:description" content="">',
        `<meta property="og:description" content="${route.description}">`
      );
      html = html.replace(
        '<meta property="og:image" content="">',
        `<meta property="og:image" content="${route.image}">`
      );
    }
    
    res.send(html);
  } catch (error) {
    res.status(500).send('Error loading page');
  }
});
```

### Common mistakes в social meta tags

**Image-related mistakes**: неправильні розміри зображень (too small або wrong aspect ratio) — використовуйте 1200 x 630 pixels. Relative URLs для зображень — завжди absolute URLs. HTTPS page з HTTP images — використовуйте og:image:secure_url. Images over 8MB — тримайте під 5MB. No alt text — завжди включайте og:image:alt.

**Content mistakes**: title too long (truncated) — тримайте og:title до 60-75 символів. Description too long — під 200 символів. Missing або incorrect og:url — використовуйте canonical URL. Однакові meta tags для всіх сторінок — customize для кожної сторінки.

**Technical mistakes**: використання "property" замість "name" для Twitter — Twitter використовує name="twitter:card". Not declaring OG namespace — додайте prefix="og: https://ogp.me/ns#". Забування оновлювати meta tags для SPAs — implement SSR або bot detection. Not clearing cache після updates — використовуйте debugger tools. Blocking crawlers в robots.txt — дозвольте Twitterbot, facebookexternalhit, LinkedInBot.

Семантичний HTML безпосередньо впливає на performance metrics. **Largest Contentful Paint (LCP)** покращується через lighter file size та browser optimization. Target: **< 2.5 секунд**. **First Input Delay (FID)** мінімізується через reduced JavaScript для interactive elements. Target: **< 100 мілісекунд**. **Cumulative Layout Shift (CLS)** стабілізується через proper semantic structure. Target: **< 0.1**.

**Оптимізація стратегії**: використовуйте semantic HTML для 60-80% lighter code weight. Implement lazy loading з `loading="lazy"` для images. Defer non-critical CSS/JS. Use service workers для offline capability. Minimize DOM complexity через proper semantic structure. Implement critical CSS inline. Preload critical resources з resource hints.

**Monitoring tools**: Google PageSpeed Insights, Lighthouse (Chrome DevTools), WebPageTest, Chrome User Experience Report (CrUX), Real User Monitoring (RUM) tools.
